# BrightScale Tracker — integrated delivery workspace

Implementation route: `/workspace/`. Same repository; legacy `index.html`, offline data and cloud stores are preserved. No automatic migration or mapping of production project IDs.

## Local verification

```sh
npm ci
npm test
npm run test:sql
npm run build
npm run dev -- --port 3000
```

`npm run test:sql` executes actual PostgreSQL/RLS in PGlite/WASM with synthetic identities. It also runs the inherited SQL suite. This does **not** validate real Supabase Auth, GoTrue, remote PostgREST, email delivery or field use. Browser test fixtures are isolated under `tests/` and excluded from deployment. The normal workspace never imports them or provides a role switch.

## Infrastructure and release gate

Apply `staging/sql/001` through `005` in order **only in a separately provisioned NEW EMPTY staging project**. Do not apply them to existing services, `brightscale-scanner`, `Abre-USA`, or the production `tracker/public/private` schemas. This module is not a compatibility migration for legacy data.

Configure workspace with the new project's URL and publishable/anon key. Never enter a secret/service-role key in the browser. Existing production project URLs and production app origins are blocked. Supabase Auth test accounts are provisioned separately; professional contacts can exist without portal access. Linking their account ID is an explicit PM operation, not an email invitation.

## Server configuration (secrets stay outside Git)

- `tracker-workspace-plan`: `WORKSPACE_ALLOWED_ORIGINS`, `WORKSPACE_PM_IDS`, `WORKSPACE_PLAN_MODEL`, `OPENAI_API_KEY`; standard Supabase URL/anon environment. Unconfigured AI fails closed; manual project entry remains available. The endpoint checks the authenticated PM allowlist, accepts bounded document/context data and writes no production data.
- `tracker-workspace-receipts`: `WORKSPACE_ALLOWED_ORIGINS`, `RESEND_API_KEY`, `WORKSPACE_RECEIPT_FROM` (verified sending domain); standard Supabase server URL/anon/service environment. Checks PM ownership using the caller's JWT before reading only that project's pending queue with server credentials.
- Signed copies are queued transactionally to the signer's **server-resolved verified Auth email**. Browser cannot select recipients or mark queue rows as sent. PM explicitly dispatches pending copies. Provider acceptance is not inbox delivery. No live email tests have run.
- Deterministic provider idempotency keys protect retries within the provider window; jobs older than 23 hours require manual reconciliation, not automatic resend. Provider errors leave records pending. Configure delivery webhooks before claiming inbox delivery.

## Workflow implemented

Document upload → local PDF/text extraction or JSON-plan import → guided SMART context → optional isolated AI suggestion → PM review of customer/site/amounts/scopes/tasks/weights/criteria/dependencies/team/milestones → atomic idempotent new draft → explicit baseline freeze → legal/safety/readiness scope release → sub report or separate PM observation → explicit validation → weighted official progress → events, linked corrections, visibility restrictions and documents → independent signed CO → client milestone consent → manually recorded invoicing/receipts → checked closure.

Original contract, CO ledgers and past credits remain separate. PM observation/validation does not create subcontract credit. The existing explicit sub-report review RPC does recognize authorized credit, with no payout. Recorded money movements are records of external payments/expenses, never transfers.
